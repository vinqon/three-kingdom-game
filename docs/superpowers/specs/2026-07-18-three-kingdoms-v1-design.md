# 三国策略游戏 V1 设计规格

## 1. 目标

构建一款可在桌面与手机浏览器中运行的 H5 三国回合制策略游戏。玩家选择曹魏、蜀汉或孙吴，在公元 229 年的立体历史地图上征兵、修城、调动武将、进攻相邻城市，并与两个 AI 势力完成一局有明确胜负的游戏。

本规格整合并落实以下已确认文档：

- [基础可玩版完整方案](../../../three-kingdoms-v1-plan.md)
- [Agent 自主验收标准](../../../three-kingdoms-v1-acceptance.md)

两份文档与本规格发生冲突时，以本规格的架构边界为实现依据，以验收文档的可观察行为为完成依据。

## 2. 已选择的实现路线

采用 React + TypeScript 管理界面，Three.js 渲染 2.5D 等距历史地图，纯 TypeScript 游戏内核负责回合、战斗、AI 与存档。

不采用以下路线：

- 纯 2D 平面地图：实现快，但无法满足立体地图目标。
- 完整 RTS 级 3D：视觉潜力高，但需要大量模型、动画和实时单位逻辑，不适合 V1。

选择的路线在地图表现、开发成本和 H5 性能之间取得平衡。地图视觉接近桌面策略游戏，但玩法保持简洁回合制。

## 3. 产品范围

### 3.1 V1 包含

- 曹魏、蜀汉、孙吴三个可选势力。
- 公元 229 年单一剧本。
- 18 座核心城市与固定相邻路线。
- 每城 0～10 格兵力、1～3 点城防。
- 征兵、修城、出征、结束回合四类核心操作。
- 猛将、守将、军师三类武将。
- 公开、确定、无随机数的自动战斗。
- 两个规则型 AI 势力。
- 自动存档、两个手动存档、重新开始。
- 胜利、失败与战绩界面。
- Agent 可操作的 QA 测试模式。

### 3.2 V1 不包含

- 粮草、金币、商业或复杂经济系统。
- 战斗地形、天气、兵种和阵型。
- 统率、武力、智力等数值属性。
- 武将技能、装备、升级、忠诚、俘虏和死亡。
- 外交、随机事件、多剧本、联网与账号。
- 可操作的实时战斗场景。

## 4. 核心规则

### 4.1 武将克制

```text
军师克猛将
猛将克守将
守将克军师
```

克制方获得 2 点战力。相同类型或无武将时不获得奖励。

### 4.2 城市操作

每座城市每回合可执行一次内政操作：

- 征兵：兵力增加 1 格，上限 10。
- 修城：城防增加 1 点，上限 3。

内政不消耗其他资源。城市完成操作后显示已行动状态，下一季度重置。

### 4.3 出征

- 只能攻击路线直接相连的敌方城市。
- 出发城市至少有 2 格兵力。
- 玩家选择出征武将与 2～10 格兵力。
- 未出征兵力留在原城市。
- 确认前显示确定性的战斗预测。

武将始终驻扎在一座己方城市。出征武将跟随军队移动：进攻获胜后驻扎在目标城市，进攻失败后返回出发城市。防守武将战败时跟随残兵撤退；没有撤退路线时，自动转移到己方首都，首都已失守则转移到任意剩余己方城市。势力没有城市时，武将变为不可用状态。V1 中武将不会死亡或被俘。

### 4.4 战斗

```text
进攻方总战力 = 出征兵力格 + 进攻方克制奖励
防守方总战力 = 驻军兵力格 + 防守方克制奖励 + 城防点数
```

- 总战力高者获胜。
- 总战力相同，防守方获胜。
- 胜方损失 1 格，但至少保留 1 格。
- 败方损失 2 格，不足 2 格时归零。
- 进攻获胜：胜方进入目标城市，城防重置为 1。
- 进攻失败：进攻残兵退回出发城市。
- 防守失败：残兵撤往一座相邻己方城市；无路可退则消失。

### 4.5 胜负

- 玩家占领另外两个势力首都后胜利。
- 玩家失去首都且没有可继续作战的城市和军队时失败。

## 5. 系统架构

### 5.1 分层

```text
React UI
  ↓ commands / view models
Application Store
  ↓ actions / state snapshots
Pure Game Engine
  ↓ map ids / visual state
Three.js Map Renderer
```

各层职责：

- `game/`：纯函数规则、回合推进、战斗、撤退、胜负，不依赖 React 或 Three.js。
- `ai/`：从合法行动列表中评分并选择行动，只调用游戏内核公开 API。
- `stores/`：保存当前对局、选中对象、弹窗与镜头状态。
- `map/`：渲染地形、城市、路线、旗帜、选中与势力覆盖，不修改规则状态。
- `components/`：开始、势力选择、状态栏、城市面板、出征面板、战报、存档与结果界面。
- `save/`：校验、序列化、版本迁移和 LocalStorage 读写。
- `qa/`：固定场景、测试面板与验收辅助，不进入正常玩家流程。

### 5.2 核心数据模型

```ts
type FactionId = 'wei' | 'shu' | 'wu';
type GeneralType = 'warrior' | 'guardian' | 'strategist';

interface CityState {
  id: string;
  name: string;
  owner: FactionId;
  troops: number;
  defense: number;
  capitalOf?: FactionId;
  adjacentCityIds: string[];
  stationedGeneralId?: string;
  actedThisTurn: boolean;
}

interface GeneralState {
  id: string;
  name: string;
  faction: FactionId;
  type: GeneralType;
  cityId: string;
  actedThisTurn: boolean;
}

interface GameState {
  version: number;
  year: number;
  season: 'spring' | 'summer' | 'autumn' | 'winter';
  turnFaction: FactionId;
  playerFaction: FactionId;
  cities: Record<string, CityState>;
  generals: Record<string, GeneralState>;
  status: 'playing' | 'victory' | 'defeat';
  log: GameLogEntry[];
}
```

所有规则方法返回新状态与结构化事件，不在原状态上修改数据。

## 6. 地图设计

### 6.1 视觉结构

- 正交相机，固定等距角度，支持拖动与缩放。
- 中国东部与中部地貌使用高度图或程序化地形网格表现。
- 长江、黄河与主要湖泊使用独立水面或贴图层。
- 城市使用低多边形汉代城楼与旗帜组合模型。
- 森林、农田和山石使用实例化渲染。
- 势力控制区使用半透明颜色覆盖与边界线。
- 城市标签使用屏幕空间 HTML 层，自动避让关键 UI。

### 6.2 数据与历史表达

- V1 使用本地静态地图数据，不依赖在线瓦片服务。
- 城市坐标、名称和 229 年势力归属记录来源。
- 历史边界作为近似复原，不宣称现代测绘级精度。
- 地形影响视觉，不参与 V1 战斗公式。

### 6.3 性能边界

- 桌面平均 60 FPS，中端手机平均不低于 30 FPS。
- 常规画面 draw call 目标低于 100。
- 首次加载资源目标不超过 15MB，总资源不超过 25MB。
- 重复树木、农田、山石和士兵标识使用 `InstancedMesh`。
- 模型使用 GLB，纹理优先 WebP；需要时再引入 Meshopt/KTX2。

## 7. 主要界面

### 7.1 开始与势力选择

第一屏直接进入游戏选择，不做营销落地页。显示三张势力选项、首都、颜色与一句特点，确认后进入地图。

### 7.2 主地图

- 顶部：年份、季度、当前势力、城市数、总兵力。
- 中央：全屏 3D 地图。
- 桌面右侧：城市或军队操作面板。
- 手机底部：可拖动操作抽屉。
- 右下：结束回合。

### 7.3 战斗预测与战报

预测面板并排显示武将类型、克制箭头、兵力格、城防和最终加法算式。结算后使用相同结构显示兵力变化、撤退与城市归属，避免出现隐藏规则。

## 8. AI 设计

AI 每回合按以下顺序行动：

1. 找出首都和前线危险城市。
2. 兵力少于 3 时优先征兵。
3. 前线城防少于 2 时优先修城。
4. 枚举合法进攻，使用公开战斗公式预测结果。
5. 优先选择克制敌将、能取胜、且不会抽空后方的行动。
6. 无合适进攻时结束回合。

AI 不作弊，不读取隐藏随机数，也不产生玩家无法执行的行动。行动计算必须可终止，每个 AI 回合计算时间不超过 2 秒。

## 9. 存档与错误处理

### 9.1 存档

- 结束玩家回合后自动存档。
- 一个自动档、两个手动档。
- 存档含版本号与完整对局状态。
- 读取前执行结构校验；无效存档显示中文错误并允许清除。

### 9.2 错误处理

- 非法操作由游戏内核返回结构化错误码，UI 转为明确中文提示。
- 模型或纹理加载失败时保留可操作的简化模型，并记录错误。
- 地图初始化失败时显示恢复操作，不允许空白页面。
- AI 异常时中止当前 AI 行动并安全推进，避免死循环。

## 10. QA 与可验收性

应用支持 `?qa=1`，提供验收文档列出的固定场景。所有核心控件使用稳定 `data-testid`。QA 模式可以载入固定状态，但不得绕过实际游戏规则函数。

Agent 验收必须通过内置浏览器真实操作，覆盖桌面 1440×900、手机竖屏 390×844、手机横屏 844×390，并产出：

```text
artifacts/acceptance/report.md
artifacts/acceptance/results.json
artifacts/acceptance/screenshots/*.png
```

## 11. 测试策略

### 11.1 单元测试

- 三种克制关系与无克制关系。
- 战力计算和平局防守胜利。
- 胜败伤亡下限。
- 占城、撤退、无路可退。
- 征兵、修城与上限。
- 相邻校验和最低出征兵力。
- 回合重置与季度推进。
- 胜利、失败和存档校验。

### 11.2 集成测试

- 从势力选择到进入地图。
- 城市操作到结束回合。
- 出征预测、确认、结算和战报。
- AI 连续两个势力行动。
- 自动存档后恢复同一状态。
- QA 场景必须调用生产规则内核。

### 11.3 浏览器与视觉测试

- 使用内置浏览器执行验收文档 15 个核心用例。
- 检查控制台异常和资源加载失败。
- 对远景、近景、战斗面板、胜负界面和三个视口截图。
- 检查 3D 画布非空、地图正确构图、文字无溢出、控件无遮挡。

## 12. 分阶段交付

### 阶段 A：可运行纵切片

- 工程、测试框架与纯规则内核。
- 一张可拖动缩放的立体地图样片。
- 3 座临时城市构成一条可进攻路线。
- 三类武将、战斗预测、结算与战报。
- QA 模式首批战斗场景。

阶段 A 用于同时验证最大视觉风险和核心规则，不作为缩减后的最终目标。

### 阶段 B：完整对局

- 18 座城市、三个势力、完整路线。
- 征兵、修城、回合、AI、胜负和存档。
- 桌面与手机主流程。

### 阶段 C：视觉与验收完成

- 正式地图数据、建筑、旗帜、纹理与动效。
- 性能压缩与兼容性修正。
- 14 张必需截图、15 个核心用例和 Agent 验收报告全部通过。

## 13. 完成定义

项目只有在 [Agent 自主验收标准](../../../three-kingdoms-v1-acceptance.md) 第 14 节的八项条件全部满足后完成。阶段 A 或阶段 B 完成不等于 V1 完成。
